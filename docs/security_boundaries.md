# Границы безопасности

**Дата:** 01.11.2026
**Основание:** ТЗ §11.1, §23–§26, §28.

## 1. Категории операций

| Категория | Что в неё входит | Кто может вызывать | Состояние |
|---|---|---|---|
| **A — чтение** | состояние оборудования, измерения, события, аварии, заказы, остатки, документы | агенты через MCP, после проверки прав | реализовано частично (1С-мост), OPC UA — нет |
| **B — подготовка предложения** | проект изменения плана, параметры операции, рекомендация по последовательности | агент готовит, человек согласует | подготовка есть (эхо документа), исполнения нет |
| **C — исполнение** | вызов метода OPC UA, запись в 1С, изменение режима | **запрещено ИИ** | отключено в коде и интерфейсе |

Категория C отключена в трёх местах: `agent/tools.py` (`SCADA_WRITE_ENABLED = False`, инструмент не отдаётся модели), `agent/web_app.py` (`POST /api/scada/command` → 403), `agent/scada_agent.py` (ответ `forbidden`).

## 2. Где живёт проверка

| Проверка | Где | Что проверяет |
|---|---|---|
| Права роли на инструмент | `agent/policy.py` (план этапа E) | роль → разрешённые MCP-инструменты |
| Схема параметров | `mcp/*` (план) | типы, диапазоны, обязательные поля |
| Подтверждение человека | `tools.py`, `web_app.py`, `1С мост` | `confirmed_by` обязателен для записи |
| Ограничения 1С | BSL-мост | только `ВЫБРАТЬ`, запрет `;`, `ИЗМЕНИТЬ`, `УДАЛИТЬ`… |
| Пороговые уставки | `scada_bridge.py` | авария по min/max, детерминированно |
| Аудит | `journal.jsonl`, `events.jsonl` | каждое действие с риском и решением |

Принцип: проверка **не** реализуется текстом промпта. Модель не может «попросить» обойти проверку — проверяющий код её не спрашивает.

## 3. Что запрещено всегда

- универсальные инструменты `write_any_node`, `execute_arbitrary_method` (ТЗ §11.2);
- изменение аварийных пределов, межблокировок, логики PLC;
- прямая запись в базу 1С в обход моста;
- выполнение команд оборудованию без отдельного решения владельца;
- выдача демо-данных за реальные измерения.

## 4. Независимость от ИИ

Контур промышленной автоматики (PLC, защиты, блокировки) работает без этой системы.
Недоступность Ollama, 1С или SCADA **не должна** влиять на оборудование: платформа только читает и предлагает.

При недоступности источника система обязана:
1. показать «источник недоступен» и время последней удачной попытки;
2. не подставлять значения;
3. остановить сценарий, если без этих данных решение недопустимо.

## 5. Проверка, что запрет работает

| Тест | Что доказывает |
|---|---|
| `tests/test_sprint0.py` | инструмент категории C отсутствует у модели; вызов возвращает `policy_denied` |
| `tests/test_permissions.py` | навык нельзя активировать без утверждения человеком; правка активных инструкций запрещена |
| `verify_1c.py` | в BSL нет COM/HTTP и изменения данных |
| Негативный тест этапа E (план) | запрещённый MCP-инструмент недоступен даже по прямой просьбе модели |

## 6. Открытые вопросы безопасности

- Кто именно утверждает действие в реальной эксплуатации (роль, а не «человек»).
- Как хранится журнал: кто может его чистить и как доказывается целостность.
- Какие узлы OPC UA разрешены к чтению (список от владельца сервера).
- Нужен ли отдельный сервис подтверждений (второй канал), или достаточно интерфейса.
